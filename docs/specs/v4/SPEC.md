# rt-trading v4 SPEC: 장중 언어 모델 판단 모의 운용(서버)
> **상태**: 승인(2026-11-01), 구현 전. 사용자 결정(서버(고정 공인 IP)의 Docker 컨테이너에서 실행, 서버에서 trading-oracle은 돌리지 않음, 장중 판단은 규칙이 아니라 언어 모델이 뉴스와 함께 함, 뉴스는 네이버 뉴스 검색(NAVER API HUB)으로 받음, 판단은 하루 일곱 번, 장중 교체는 하루 2번까지, 판단에 실패하면 지금 부하를 유지, 종가 베팅 부하 `overnight`를 넣음, 통과 기준의 판단 실패 0번은 초안대로 둠, 자동 실행 명령에 시간 제한을 둠, 2026-11-02부터 기간을 셈)을 반영했다. **[확인 필요]**는 실데이터 실행 전에 확인할 사실이다.

상위 문서: [intent.md](../../../intent.md) · 이전 스펙: [v3](../v3/SPEC.md)

v3 헤드는 거래일마다 개장 전에 한 번 부하를 고른다. v4는 이것을 하루 일곱 번으로 늘린다. 개장 전에는 그날 쓸 부하를 고르고, 장중에는 매시 그날의 시세와 뉴스 검색 결과를 보고 부하를 바꿀지 정하고, 마감 전에는 밤사이에 무엇을 들고 갈지 정한다.
판단은 언어 모델이 하고, 교체 횟수·손실 한도·실패 처리는 코드가 강제한다.
항상 켜 둔 서버의 Docker 컨테이너에서 돌고, 주문 없이 1주 동안 모의 운용해 검증한다. v4는 주문을 내지 않는다.

## 근거와 한계

- 한국 지수의 상승은 대부분 밤사이에 났다. KODEX 200 수정 시가·종가(2002-10~2026-10, 비용 전)로 나누면 밤사이(전 거래일 종가→시가) 누적 +3,756%, 장중(시가→종가) −55%였다(2026-10-30 확인). KOSPI 연구(고강석 2012, 김선웅 2022)와 해외 분석(Knuteson 2021, KOSPI 1996~2021)도 같은 방향이다. 그래서 마감 전 판단을 따로 두고, 종가에 사서 다음 날 시가에 파는 부하 `overnight`를 넣는다(4.1).
- 같은 규칙을 매일 하면 왕복 수수료(0.0376%)가 밤사이 평균 수익(하루 0.0616%)의 약 61%를 가져간다. v0 결과는 +315%, 최대 낙폭 44.30%였다. `overnight`는 매일 쓸 전략이 아니라 헤드가 고를 때만 쓰는 도구다.
- 전날 미국장 정보는 대부분 한국 시가에 반영되고, 시가 뒤 장중 수익과는 관계가 거의 없다(v3 근거와 같다. 2026년 일봉으로 다시 보면 SPY 수익률과 다음 날 KODEX 200 시가 갭의 상관은 0.57, 시가→종가와는 −0.06).
- 장중 모멘텀은 통계적으로 있지만, 최근 재현에서 거래당 우위가 프로젝트 수수료와 비슷하거나 작았다(Zarattini·Aziz·Barbon 2024의 독립 재현들). 장중 교체가 잦으면 비용이 쌓이므로 횟수를 제한한다(3.4).
- 언어 모델이 뉴스로 개별 종목의 다음 날 수익을 예측한 연구가 있지만 우위가 해마다 줄었다(Lopez-Lira·Tang, 연환산 샤프 2021년 4분기 6.54 → 2024년 1~5월 1.22, 비용 전). 지수 ETF를 장중에 바꾸는 데 효과가 있다는 연구는 찾지 못했다. 뉴스 판단의 효과는 앞으로의 모의 운용으로만 확인한다.
- 언어 모델은 학습한 기간의 시세와 뉴스를 기억한다(v3 근거와 같다). 그래서 과거 뉴스로 헤드를 시험하지 않는다.
- 1주(5거래일) 모의 운용은 실력 시험이 아니라 판단·정산·보고가 사고 없이 도는지 보는 작동 확인이다(v3와 같다).

## 0. 완결성 계약

- v4는 토스 캔들 조회(v3와 같고, 장중 판단 때는 당일 1분봉을 더 받는다), 네이버 뉴스 검색(NAVER API HUB), Codex 호출만 한다. 주문·계좌 API는 부르지 않는다.
- Codex에는 3.2의 입력만 보낸다. 계좌 정보와 토스·네이버·Codex 인증 정보는 보내지 않는다.
- v0~v3의 명령과 동작은 그대로 둔다. 엔진·헤드·시세 코드를 함께 쓰되, 각 버전의 acceptance가 계속 통과해야 한다.
- `uv run rt-trading v4-acceptance`는 네트워크와 인증 정보 없이, 가상 시세·가상 뉴스 fixture와 가짜 Codex만으로 9절의 기준을 실행한다. 모두 통과하면 exit 0이다.
- 서버의 Docker 컨테이너에서 `v4-serve`가 평일 일정(5.1)대로 판단·정산·보고를 자동으로 돌리고, 현황을 보기 전용 웹페이지로 확인할 수 있다.
- 실데이터로 한 거래일의 모든 판단, 그 날의 정산, 보고서를 한 번 만든다.
- 위 조건을 충족하면 v4는 완료다. 모의 운용 기간이 다 지나는 것과 헤드의 통과 여부는 완료 조건이 아니다.

| PRD 03 장중 교체 엔진 | 장중 교체 체결, `overnight` 부하, 계좌 실행과 비교 계좌 | 부하와 계좌 |
| PRD 04 실행과 보고 | 정산, 계좌 요약, `v4-daily`, `v4-decide`, 보고서와 판정, `v4-acceptance` | 실행, 판정과 보고서 |
| PRD 05 서버 실행 환경 | 서버 Docker, 일정 실행, 보기 전용 현황 웹페이지, 맥북에서 넘어오기, 실데이터 첫날 | 실행 환경과 현황 |

- PRD 01→05 순서로 구현한다. 각 PRD는 자기 acceptance가 통과하고 앞 PRD의 acceptance도 계속 통과하면 완료다.
- 9절의 각 항목은 정확히 한 PRD가 맡는다. PRD 05까지 완료하면 v4가 완료된다.

## 1. 목표와 비목표

### 목표

- 헤드가 거래일마다 판단 시각(3.1)마다 부하 하나를 고르고, 이유와 운용 노트를 남긴다.
- 모든 판단은 판단 시각 전에 나온 뉴스 검색 결과를 함께 본다. 장중·마감 전 판단은 그날의 장중 시세 요약도 본다.
- 고른 부하가 판단 마감 뒤 체결 시각(3.1)부터 그날의 실제 1분봉으로 모의 매매한다.
- 같은 기간 아침 판단 계좌, 규칙 헤드 계좌, 부하별 계좌를 함께 돌려 비교한다(4.3).
- 정한 기간이 끝나면 6절 기준으로 판정한다.
- 서버의 Docker 컨테이너에서 자동으로 돌고, 사람은 보기 전용 웹페이지로 현황을 확인한다.

### 비목표

- 실제 주문, 계좌·잔고 조회
- 헤드가 부하 코드를 만들거나 부하의 숫자를 고치는 것(v3 부록 A)
- 거래 대상 넓히기(다른 ETF, 채권·해외지수 ETF), 레버리지 상품
- 정규장 밖 거래와 넥스트레이드 체결. ETF는 넥스트레이드 거래 대상이 아니다(한국경제 2026-10-29 보도).
- 기사 본문 수집. 검색 API가 주는 제목과 요약만 쓴다. 웹 검색과 거시 지표도 넣지 않는다.
- 규칙이 장중 판단을 대신하는 것(사용자 결정)
- 웹 관리 기능(시작·중지·설정 바꾸기)
- 진행 중인 v3 모의 운용을 서버로 옮기는 것. v3는 맥북에서 기간을 마친다.

## 3. 헤드

### 3.1 판단 시각과 마감

| 판단 | 판단 시각 T | 마감 | 교체 체결 |
| --- | --- | --- | --- |
| 개장 전 | 아침 실행(5.1) 안에서 입력을 만드는 시각 | 개장 10분 전(v3 3.4) | 시가 동시호가(v3 4.2) |
| 장중 | 개장 1시간 뒤부터 마감 1시간 30분 전까지 매시 정각 | T + 5분 | T + 5분에 시작하는 1분봉의 시가 |
| 마감 전 | 마감 20분 전 | T + 5분 | T + 5분에 시작하는 1분봉의 시가 |

- 정상일(09:00~15:30)은 08:50 마감의 개장 전 판단, 10:00·11:00·12:00·13:00·14:00 장중 판단, 15:10 마감 전 판단으로 하루 일곱 번이다. 장 일정 표(v3 5.2)로 시각을 옮긴다. 연초 첫 거래일(10:00~15:30)은 여섯 번, 수능일(10:00~16:30)은 일곱 번이다.
- 장중·마감 전 판단은 T까지 끝난 1분봉으로 하고, 교체는 엔진에서 T + 5분에 끝나는 봉이 끝날 때 주문을 내 다음 봉 시가에 체결하는 것과 같다. 판단과 체결 사이가 5분 떨어져 있어 판단이 체결가를 미리 알 수 없다.
- 모델, 호출 방식, 형식 검사는 v3 3.1과 같다. 장중·마감 전 판단은 실패하면 마감 전까지 다시 부른다. 다시 부르는 간격은 PRD 02에서 정한다.
- 응답을 받아 검증까지 마친 시각이 마감 전이어야 한다.

### 3.2 입력

v3 3.2의 항목을 주고, 아래 항목을 바꾸거나 더한다. 판단 시각 T 뒤의 시세와 기사는 넣지 않는다. 시세는 v3처럼 가격 자체를 보내지 않고 수익률과 비율(%)로만 보낸다. 계좌 요약은 정산을 마친 날까지의 값이고, 오늘 장중의 계좌 상태는 넣지 않는다.

| 항목 | 내용 |
| --- | --- |
| 판단 | 종류(`pre_open`, `intraday`, `pre_close`), 마감 시각, 지금 부하, 오늘 남은 장중 교체 횟수(3.4) |
| 오늘 시세 | 장중·마감 전 판단에만 준다. 두 종목의 T까지 끝난 1분봉으로 계산한 전 거래일 종가 대비 수익률, 오늘 시가 대비 수익률, 오늘 고가·저가 사이의 위치, 최근 30분 수익률, 개장부터 30분 단위 수익률. 받지 못하면 `null` |
| 뉴스 | T 전에 나온 기사의 제목, 요약, 언론사 도메인, 나온 시각(PRD 01). 받지 못하면 `null` |
| 아침 판단 계좌 | 아침 판단 계좌(4.3)의 시작 뒤 수익률과 최대 낙폭 |
| 지난 판단 | v3의 지난 판단을 판단 차례 단위로 바꾼다. T 전의 최근 20개 판단(오늘 앞선 판단 포함)의 날짜, 차례, 종류, 상태(`capped` 포함), 부하, 이유와 그날 헤드 계좌 수익률 |

### 3.3 출력

- v3 3.3과 같다(`{"subordinate": ..., "reason": ..., "notes": ...}`).
- 지금 부하와 같은 id면 교체하지 않는다.
- 운용 노트는 그날의 다음 판단과 다음 거래일의 첫 판단으로 이어진다.

### 3.4 실패와 교체 한도

- 마감까지 올바른 응답을 받지 못했거나 판단을 하지 않은 시각은 지금 부하를 유지하고 판단 실패로 센다. 서버가 꺼져 있던 시각도 포함하고, 상태는 `missing`이다(사용자 결정).
- 개장 전 판단이 실패하면 전 거래일 마감 때의 부하를 이어 간다(v3는 `cash`였다).
- 장중·마감 전 판단에 따른 교체는 하루 2번까지다(사용자 결정). 2번을 다 쓴 뒤의 교체 응답은 기록만 하고 실행하지 않는다. 상태는 `capped`이고 판단 실패가 아니다. 개장 전 판단의 교체는 세지 않는다.
- 기록한 판단은 바꾸지 않는다.

## 4. 부하

### 4.1 목록

v3 4.1의 여덟 부하에 다음 하나를 더한다.

| id | 내용 | 엔진 방식 |
| --- | --- | --- |
| `overnight` | 마감 10분 전 봉이 끝날 때 KODEX 200 매수 주문을 내 종가 동시호가에 사고, 다음 거래일 시가 동시호가에 판다. v0 4.1의 종가 베팅을 1분봉 엔진으로 옮긴 것이다 | 며칠 보유 |

- 헤드 입력에 주는 `overnight`의 백테스트 결과는 v0 결과(2002-10~2026-10 총수익 +315.3%, 최대 낙폭 44.30%)다.
- 부하의 숫자는 원래 스펙 그대로다.

### 4.2 장중 교체

- 장중·마감 전 판단으로 부하가 바뀌면 교체 체결 봉(3.1)에서 다음을 한다.
  - 전 부하가 남긴 대기 주문은 취소한다.
  - 보유가 있으면 그 봉 시가에서 한 단계 불리한 호가로 판다(사유 `switch_head`).
  - 새 부하는 그 매도 뒤의 현금 상태에서, 그 봉부터 자기 규칙을 적용한다. `hold_kodex200`·`hold_inverse`는 같은 봉 시가에서 한 단계 불리한 호가로 산다.
- 새 부하는 그날 이미 지난 시각에 하는 동작을 하지 않는다. 예를 들어 15:00 매수 시각이 지난 뒤 `last_half_hour`로 바뀌면 그날은 사지 않는다. 지난 시각의 시세로 계산하는 신호는 쓴다.
- 개장 전 판단의 교체는 v3 4.2와 같다.
- 종가 동시호가 구간에는 교체하지 않는다. 마감 전 판단의 교체 체결 봉이 하루의 마지막 교체 기회다.
- 결함일과 기간 마지막 거래일은 v3 4.2와 같다.

| 계좌 | 규칙 |
| --- | --- |
| 아침 판단 | 헤드의 개장 전 판단만 따르고 장중·마감 전 판단은 무시한다. 장중 판단의 값어치를 헤드 계좌와의 차이로 본다. Codex를 더 부르지 않는다 |
| 규칙 헤드 | v3 4.3과 같다 |
| 부하 계좌 | v3 4.3과 같다(`overnight` 계좌가 더해진다) |

## 5. 실행

### 5.1 일정

서버 시각과 상관없이 모든 시각은 한국 시간으로 계산한다.

| 시각 | 하는 일 |
| --- | --- |
| 07:30, 08:20 | `v4-daily`: v3 5.1과 같다(미국·국내 시세 받기와 검증, 밀린 날 정산, 개장 전 판단). 판단에 v4 헤드와 뉴스를 쓴다. 같은 날 두 번 실행해도 결과가 같다 |
| 장중·마감 전 판단 시각 T | `v4-decide`: 당일 1분봉(T까지 끝난 봉)과 뉴스를 받아 판단한다. 시세와 뉴스는 T + 2분까지만 받고, 넘기면 받은 데까지로 판단한다 |

- 꺼져 있다가 켜지면 마감이 지난 판단 시각은 실행하지 않는다. 그 시각은 정산 때 `missing`으로 기록된다.
- 정산은 v3처럼 다음 거래일 아침 `v4-daily`가 그날 확정된 1분봉으로 한다. 장중에 받은 당일 1분봉은 판단 입력에만 쓴다.

### 5.2 휴장일, 장 일정, 정산

v3 5.2~5.3과 같다. 정산은 그날의 판단 기록(차례, 상태, 부하)에 따라 계좌별로 하루를 돌린다.

## 6. 통과 기준

기간의 5거래일을 모두 정산하면 판정한다. 헤드 계좌가 다음을 모두 만족하면 통과다.

1. 모든 판단 시각에 마감 전 올바른 판단을 기록했다(판단 실패 0번). `capped`는 실패가 아니다.
2. 최대 낙폭(v1 SPEC 6절의 식, 1분봉 평가 자산)이 20%보다 작다.

- 5거래일이면 판단이 35번 안팎이고, 한 번이라도 실패하면 불통과다.
- 수익과 비교 계좌와의 차이(특히 아침 판단 계좌와의 차이)는 보고서에 적지만 판정에 넣지 않는다.
- 기간 중에 사람이 지시문, 입력 항목, 검색어, 판단 시각, 부하 목록이나 숫자, 모델을 바꾸면 그날부터 새 기간으로 다시 센다(intent).
- 통과해도 실계좌 운용 승인이 아니다.

## 7. 산출물

- `data/v4/paper.sqlite3`: 판단(날짜, 차례, 종류, 상태 `ok`·`capped`·`late`·`invalid`·`failed`·`missing`, 부하, 이유)과 정산한 날
- `data/v4/market.sqlite3`: 정산한 날까지의 시세 사본(v3 7절과 같다)

## 9. Acceptance Criteria

`v4-acceptance`는 손으로 만든 가상 시세·가상 뉴스 fixture와, 미리 적어 둔 응답과 오류를 돌려주는 가짜 Codex만 쓴다. 기대값은 손으로 미리 계산해 둔다. v3 9절 사례 중 v4가 그대로 쓰는 코드의 사례(형식 오류, 체결가·수수료·인버스 세금·정수 주, 결함일, 휴장일, 정산 순서, 보고서 형식, 현황 웹페이지)는 PRD에서 골라 옮겨 적는다.

- 뉴스
  - 판단 시각 T 뒤에 나온 기사는 입력에 없다. 같은 원문 링크의 기사는 한 번만 들어간다. 제목과 요약의 HTML 태그는 지워진다.
  - 뉴스 받기가 실패하면 입력의 뉴스가 `null`이고 판단은 계속한다.
- 헤드
  - T 뒤의 시세(당일 1분봉 포함)와 기사를 바꿔도 입력이 같다. 입력에 가격 자체, 계좌 번호, 인증 정보가 없다.
  - 판단 차례가 정상일·10시 개장일·수능일의 장 일정에 맞고(3.1), 교체 시각은 모두 종가 동시호가 구간보다 이르다.
  - 장중 판단은 마감(T + 5분) 전에 검증까지 마치면 정상이다. 마감 뒤에 마치거나 실패하면 지금 부하 유지와 판단 실패로 기록된다.
  - 개장 전 판단이 실패하면 전 거래일 마감 때의 부하가 이어진다.
  - 장중·마감 전 교체가 하루 2번을 넘으면 세 번째부터 `capped`로 기록되고 실행되지 않는다. 개장 전 교체는 세지 않는다.
  - 오늘 앞선 판단과 운용 노트가 다음 판단 입력에 들어간다.
- 부하와 계좌
  - 장중 교체는 T + 5분에 시작하는 봉의 시가에서 한 단계 불리한 호가로 판 뒤 새 부하가 현금에서 시작한다. `hold_*`는 같은 봉에서 산다. 이미 지난 시각의 동작은 하지 않는다.
  - `overnight`는 마감 10분 전 봉이 끝날 때 매수 주문을 내 종가 동시호가에 사고, 다음 거래일 시가 동시호가에 판다.
  - 아침 판단 계좌는 장중·마감 전 판단을 무시한다.
- 실행
  - 판단 시각마다 한 번 실행하고, 마감이 지난 시각은 실행하지 않는다. 같은 시각을 두 번 실행해도 판단이 다시 생기지 않는다.
  - 시세와 뉴스 받기는 T + 2분까지만 한다.
  - 정산은 판단 기록이 없는 판단 차례마다 `missing`을 넣는다.
- 판정과 보고서
  - 6절의 경계: 판단 실패가 한 번이라도 있으면 불통과다. `capped`만 있으면 통과할 수 있다. 최대 낙폭이 정확히 20%면 불통과다.
- 실행 환경과 현황
  - 아침 실행 차례와 판단 차례가 정상일·10시 개장일·수능일의 장 일정(3.1)과 판단 마감에 맞고, 휴장일과 주말에는 판단하지 않는다. 늦게 켜져도 마감 전이면 그 차례를 한 번 실행하고, 지났으면 실행하지 않는다.
  - 현황 웹페이지는 GET 요청에만 답하고, 오늘의 판단을 차례별로 보여 준다. 판단 이유 속 HTML은 글자 그대로 보이고, 페이지를 열어도 저장된 파일이 바뀌지 않는다.

## 10. 실데이터 실행 전 확인할 것

- **[확인 필요] 토스 약관**: v3 10절과 같다. v4는 시세 요약을 뉴스와 함께 하루 일곱 번 Codex로 보낸다.
- **[확인 필요] NAVER API HUB 이용 약관**: 검색 결과(제목·요약)를 저장하고 Codex로 보내는 것이 허용되는지 확인한다.
- **[확인 필요] NAVER API HUB 요금**: 지금은 한시적으로 무료이고, 유료로 바뀌면 미리 공지한다(NCP 사용 가이드). 콘솔의 이용 한도와 알림을 v4 사용량에 맞춰 낮게 걸어 둔다.
- **[확인 필요] Codex 사용량**: 하루 일곱 번과 재시도가 계정 사용량 한도 안인지 확인한다.
- **[확인 필요] 토스 당일 1분봉**: 장중에 당일 1분봉을 몇 분 늦게 주는지 확인한다. 늦으면 3.2의 "T까지 끝난 봉"이 비게 된다.
- **[확인 필요] Codex 토큰**: 서버에는 trading-oracle을 두지 않으므로, 맥에서 로그인해 만든 토큰 파일(`~/.trading-oracle/auth/codex.json`)을 서버로 옮겨 쓴다. 한쪽에서 토큰을 갱신하면 다른 쪽 토큰이 끊기는지 확인하고, 끊긴다면 v4 운용 중에는 맥의 trading-oracle을 쓰지 않는다.
- 서버의 고정 공인 IP가 토스 허용 IP에 등록되어 있다.
- 네이버 클라우드 플랫폼(NCP)에서 NAVER API HUB 이용을 신청하고, 검색 API로 Application을 등록해 받은 Client ID와 Client Secret이 서버의 `.env`에 `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET`으로 있다(맥의 `.env`로 2026-11-01에 시험 호출이 됐다). 네이버 개발자센터의 검색 API는 2026-07-31부터 새로 신청할 수 없다(개발자센터 공지 2026-06-29). 호출 주소는 `https://naverapihub.apigw.ntruss.com/search/v1/news`, 인증 헤더는 `X-NCP-APIGW-API-KEY-ID`·`X-NCP-APIGW-API-KEY`이고, 한도는 월 775,000건, 키당 초당 50건이다.
- 맥북의 v3 컨테이너를 멈췄다. 같은 토스 키를 두 곳에서 쓰면 토큰이 서로 끊긴다(v3 10절).
- 서버 시계가 맞고, 휴장일 표와 장 일정 표가 기간을 덮는다. 기간에 수능일이 있으면 KRX 공지로 확인해 장 일정 표에 넣는다.
