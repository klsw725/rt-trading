# PRD: v4 PRD 05 서버 실행 환경
> **상태**: 초안, 구현 전
> 상위 SPEC: [v4 SPEC](../SPEC.md)

## 의존성

- PRD 04의 `v4-daily`, `v4-decide`, `v4-report`, 기간과 휴장일 표, `paper.sqlite3`의 `decisions`·`settled_days` 표, `v4-*` 보고서
- PRD 02의 판단 차례와 계획 부하
- v3 PRD 05의 자동 실행·현황 웹페이지 방식(`v3_serve`)과 컨테이너(`Dockerfile`, `.dockerignore`, `compose.yaml`)
- 고정 공인 IP와 Docker가 있는 서버, Codex 토큰 파일 `~/.trading-oracle/auth/codex.json`, 저장소 루트의 `.env`

## 문제

판단이 하루 일곱 번이고 장중 판단은 5분 안에 끝나야 한다. 한 차례라도 놓치면 판단 실패다.
맥북은 잠들 수 있어서, 꺼지지 않는 서버에서 정해진 시각마다 빠짐없이 실행하고, 사람은 현황을 보기만 해야 한다.

## 목표

1. 서버의 Docker 컨테이너에서 아침에는 `v4-daily`와 `v4-report`를, 판단 차례마다 `v4-decide`를 자동 실행한다(SPEC 5.1).
2. 오늘의 판단을 차례별로 보여 주는 보기 전용 현황 웹페이지를 연다(SPEC 8절).
3. 맥북에서 서버로 넘어오고, 실데이터로 첫 거래일의 모든 판단과 정산, 보고서를 만든다(SPEC 0절).

## 범위 밖

- 판단, 계좌 실행, 정산, 보고서 자체(PRD 01~04)
- 웹에서 실행·중지·설정을 바꾸는 조작
- 서버 밖에서 웹페이지를 바로 여는 것. 사용자는 SSH 터널로만 본다

## 자동 실행

- `v4-serve`는 10초마다 한국 시각으로 실행 차례를 보고, 아직 실행하지 않은 차례이면 그 차례의 명령을 실행한다. 컨테이너의 시간대와 상관없이 한국 시각으로 계산한다.
- 실행 차례는 두 가지다.

| 차례 | 언제 | 실행 |
| --- | --- | --- |
| 아침 | 평일(월~금)의 07:30과 08:20 중 이미 지난 마지막 시각. 09:50부터는 없다(v3 PRD 05와 같다) | `rt-trading v4-daily`, 이어서 `rt-trading v4-report`. 앞 명령이 실패해도 뒤 명령을 실행한다 |
| 판단 | 기간의 거래일에, 그날의 `intraday`·`pre_close` 차례 s(PRD 02)마다 s ≤ 지금 < s + 5분일 때 | `rt-trading v4-decide --at s` |

- 그래서 늦게 켜져도 판단 마감 전이면 그 차례를 바로 한 번 실행하고, 마감이 지났으면 실행하지 않는다. 휴장일 판단은 아침 차례는 `v4-daily`가, 판단 차례는 이 자동 실행이 휴장일 표로 한다.
- 같은 차례는 다시 실행하지 않는다. 한 차례를 실행하는 동안 다른 차례가 오면, 끝난 뒤 그 차례가 아직 유효하면 실행한다.
- 명령마다 시간 제한이 있다(사용자 결정). 판단 차례의 `v4-decide --at s`는 마감 1분 뒤(s + 6분)에, 아침 차례의 `v4-daily`·`v4-report`는 09:55에 끝나지 않았으면 멈춘다. 멈춘 명령 하나가 남은 차례를 모두 막지 않게 하려는 것이다. 마감 뒤 1분은 마감 직전에 마친 판단이 기록을 끝낼 여유이고, 09:55는 가장 이른 판단 차례(10:00) 전이다.
- 멈춘 명령은 실행 기록에 `V4_COMMAND_TIMEOUT: {HH:MM}까지 마치지 못해 멈췄다({명령})` 줄을 남기고, 마지막 실행 상태에는 그 명령의 종료 코드 대신 시간 초과를 남긴다. 그 뒤 차례는 그대로 실행한다.
- 실행할 때마다 `data/v4/run.log`에 `=== YYYY-MM-DD HH:MM:SS {차례} ===`(시작한 한국 시각과 차례 이름) 한 줄을 쓰고, 명령의 표준 출력과 표준 오류를 이어 쓴다. 차례 이름은 아침이면 `아침 07:30`처럼, 판단이면 `판단 10:00`처럼 쓴다.
- 10초마다 하는 한 번의 확인(시계와 명령 실행 함수를 받는다)을 따로 둔다. acceptance가 가짜 시계와 가짜 명령 실행 함수를 끼운다.
- 다음 실행 예정 시각은 지금보다 뒤인 첫 차례의 시작 시각이다.
- 실행 중인지와, 켠 뒤 마지막 실행의 차례·시작·끝 시각과 명령마다의 종료 코드를 기억해 웹페이지에 보여 준다.

## 컨테이너

- 이미지는 v3와 같은 `Dockerfile`로 만든다.
- `compose.yaml`에 서비스 `v4`를 더한다. `v3` 서비스와 같은 빌드와 연결(`data/`, 읽기 전용 `.env`, `~/.trading-oracle/auth/`)을 쓰고, 명령은 `rt-trading v4-serve --host 0.0.0.0`, 포트는 `127.0.0.1:8081:8081`, `restart: unless-stopped`다.
- 서버에서는 `docker compose up -d --build v4`로 v4만 켜고 `docker compose stop v4`로 멈춘다. 다른 명령은 `docker compose run --rm v4 rt-trading <명령>`으로 실행한다. 코드나 `v4_period.json`·`krx_holidays.csv`·`krx_sessions.csv`를 바꾸면 같은 명령으로 다시 만든다.

## 현황 웹페이지

v3 PRD 05의 현황 웹페이지와 같고 다음을 바꾼다.

- 포트는 8081이다. 컨테이너 밖으로는 서버의 `127.0.0.1:8081`에만 열리고, 사용자는 `ssh -L 8081:127.0.0.1:8081 {서버}`로 터널을 연 뒤 자기 컴퓨터의 `http://127.0.0.1:8081`로 본다.
- 묶음은 위에서부터 다음과 같다.

| 묶음 | 내용 |
| --- | --- |
| 자동 실행 | `상태: 대기 중` 또는 `상태: 실행 중({차례}, {시작 시각} 시작)`. `마지막 실행: {차례}, {시작 시각} 시작, {끝난 시각} 끝, {명령} 종료 코드 {n}`(명령마다, 시간 제한에 걸린 명령은 `{명령} 시간 초과`) 또는 `마지막 실행: 없음({켠 시각}에 켠 뒤)`. `다음 실행: {YYYY-MM-DD HH:MM}`. `페이지 시각: {YYYY-MM-DD HH:MM:SS}` |
| 기간 | v3와 같다 |
| 오늘 판단 | 오늘이 기간의 거래일일 때만 보인다. `지금 부하: {id}, 남은 교체 {n}번`(PRD 02의 계획 부하로 계산)과, 오늘의 판단 차례마다 `차례`, `종류`, `상태`, `부하`, `이유`. 행이 없는 차례의 상태는 마감 전이면 `대기`, 마감 뒤면 `없음`이다 |
| 판단 | 기간 안의 오늘 전 판단 행. 열은 `날짜`, `차례`, `종류`, `상태`, `부하`, `이유`이고 (날짜, 차례) 순이다 |
| 계좌 | v3와 같고, `data/reports/`의 `v4-*` 보고서 중 이름순으로 가장 뒤의 것을 쓴다 |
| 최근 실행 기록 | `data/v4/run.log`의 마지막 40줄. 없으면 `기록 없음` |

## 맥북에서 넘어오기

코드가 없는 운영 절차다. 완료 조건에서 차례대로 한다.

1. 서버에 저장소를 받고, 맥북의 `.env`(토스·네이버 인증 정보)를 서버 저장소 루트로 옮긴다. 파일 권한은 소유자만 읽게 한다.
2. 맥북의 `~/.trading-oracle/auth/codex.json`을 서버의 같은 위치로 옮긴다(SPEC 10절의 Codex 토큰 확인).
3. 서버의 공인 IP를 토스 허용 IP에 등록하고, 기간 전 거래일에 `docker compose run --rm v4 rt-trading fetch`와 `docker compose run --rm v4 rt-trading v3-us-fetch`로 시세 받기가 되는지 확인한다.
4. 맥북의 v3 모의 운용 기간(2026-10-30~11-05)이 끝나면 맥북에서 `docker compose down`으로 v3를 멈춘다. 같은 토스 키를 두 곳에서 쓰면 토큰이 서로 끊긴다.
5. `v4_period.json`에 시작일을 적고, 서버에서 `docker compose up -d --build v4`로 켠다.

## 가상 fixture

- 실행 차례 사례마다 한국 시각, 기간 설정, 기대하는 차례(없으면 `null`), 다음 실행 예정 시각을 적는다.
  - 정상일 2026-01-05: 07:29:59, 07:30, 08:19:59, 08:20, 09:49:59, 09:50, 10:00, 10:04:59, 10:05, 15:10, 15:14:59, 15:15
  - 연초 첫 거래일 2026-01-02: 10:00(차례 없음), 11:00
  - 수능일 2025-11-13: 15:00, 16:10
  - 기간 사이에 낀 평일 휴장일 2026-12-31(07:30에는 아침 차례가 있고 10:00에는 판단 차례가 없다)과 토요일
  - 기간 전 평일의 10:00(판단 차례가 없다)
- 자동 실행 사례는 한 번의 확인을 시각 순서대로 부르고, 시각마다 실행할 명령과 받은 초, 끝난 뒤의 실행 기록·마지막 실행 상태를 적는다. 가짜 명령 실행 함수는 받은 초를 기록하고 `{명령} 출력` 한 줄을 쓰고, 정해 둔 종료 코드를 돌려준다. 시간 초과로 정해 둔 명령에서는 가짜 시계를 받은 초만큼 움직이고 시간 초과를 돌려준다.
- 현황 페이지 사례는 임시 디렉터리에 기간 설정과 휴장일 표, 오늘의 판단 일부와 지난 날 판단·정산한 날을 넣은 `paper.sqlite3`, 이름이 다른 보고서 두 개, 45줄짜리 실행 기록을 만들고, 자동 실행 상태와 지금 시각을 준다. 판단 이유 하나에 `<script>`를 넣는다. 첫날처럼 `settled_days` 표가 없는 `paper.sqlite3`로도 페이지를 만든다.
- 임시 포트에서 웹페이지를 띄워 요청하고, 페이지에 있어야 할 글자와 없어야 할 글자를 손으로 적어 비교한다.

## 필수 Acceptance

SPEC 9절의 "실행 환경과 현황" 항목을 맡는다.

- 실행 차례가 정상일·연초 첫 거래일·수능일의 아침 차례와 판단 차례, 판단 마감(s + 5분)과 09:50 경계, 기간 밖, 휴장일, 주말에 맞고, 다음 실행 예정 시각이 맞다. 늦게 켜져도 마감 전이면 그 차례를 한 번 실행하고, 지났으면 실행하지 않는다. 같은 차례는 다시 실행하지 않는다.
- 아침 차례마다 `v4-daily`와 `v4-report`를 차례로 한 번씩 실행하고(`v4-daily`가 실패해도), 판단 차례마다 `v4-decide --at {차례}`를 한 번 실행한다. 실행 기록에 시작 시각·차례 줄과 명령 출력이, 마지막 실행 상태에 종료 코드가 남는다.
- 명령에는 시간 제한(판단 차례 s + 6분, 아침 차례 09:55)까지 남은 초를 준다. 그때까지 끝나지 않은 명령은 실행 기록에 `V4_COMMAND_TIMEOUT`을, 마지막 실행 상태와 웹페이지에 시간 초과를 남기고, 다음 차례는 그대로 실행한다.
- `GET /`의 페이지에 자동 실행 상태, 기간과 정산 진행, 오늘 판단(지금 부하, 남은 교체 횟수, 차례별 상태·부하·이유와 `대기`·`없음`), 지난 판단, 최신 보고서의 계좌 지표와 판정, 실행 기록 마지막 40줄이 나온다. 옛 보고서의 값과 마지막 40줄 앞의 기록은 나오지 않고, 이유 속 `<script>`는 글자로 보인다. 다른 경로는 404, POST는 501이다. `settled_days` 표가 없는 첫날 `paper.sqlite3`로 만들면 `정산 0/5 (마친 마지막 날 없음)`이 나오고, 페이지를 열어도 파일이 바뀌지 않는다(v3에서 옮긴 사례).

## 완료 조건 (v4 완료)

- `uv run rt-trading v4-acceptance`가 exit 0이다.
- `cli.py`를 바꾸므로 `uv run rt-trading acceptance`, `v0-acceptance`, `v2-acceptance`, `v3-acceptance`로 기존 명령이 그대로인지 확인한다.
- 위 "맥북에서 넘어오기"를 마치고, 서버에서 `docker compose up -d --build v4`로 켠 뒤 SSH 터널로 현황이 보이는지 확인한다.
- SPEC 10절을 확인한 뒤 실데이터로 다음을 한다.
  1. 기간 첫날 자동 실행으로 개장 전·장중·마감 전 판단이 모두 기록된다.
  2. 다음 거래일 아침 자동 실행으로 첫날을 정산하고 보고서를 만든다.
  3. 웹페이지에서 판단, 정산 진행, 계좌 지표를 확인한다.
- SPEC과 모든 PRD의 상태를 "구현 완료"로 바꾼다. 모의 운용 기간이 다 지나는 것과 판정 결과는 완료 조건이 아니다.
